# 闲鱼登录架构开源复核（2026-08-21）

## 结论先行

截至 2026 年 8 月 21 日，对公开仓库做源码级核对后，没有找到能够稳定绕过闲鱼风控、保证多账号登录的可信方案。多个项目仍会遇到 `FAIL_SYS_USER_VALIDATE`、滑块完成但 `x5sec` 未更新、手动更新 Cookie 后再次掉线等问题。

因此，本项目当前两个账号都无法登录，不能继续按“滑块坐标算法”方向堆补丁。更可能的根因是平台侧对服务器 IP、浏览器指纹、Cookie、设备信息和账号状态的联合校验；前端显示滑块成功不等于服务端已经放行。

## 调查范围

本次拉取并检查了以下公开仓库的 README、配置和登录/凭据相关代码：

- `23Star/xianyu-super-butler`
- `zhinianboke/xianyu-auto-reply`
- `GuDong2003/xianyu-auto-reply-fix`
- `dameng2026/xianyu-pilot`
- `JianGuoPaPa/xianyu-auto-agent-local-console`

这些仓库的最近提交时间集中在 2026 年 8 月 14 日至 2026 年 8 月 21 日，但“最近更新”并不代表能消除平台风控。

## 可借鉴做法

### 1. 本机真实浏览器作为登录源

`JianGuoPaPa/xianyu-auto-agent-local-console` 把自己的 Goofish/闲鱼网页 Cookie 作为输入，并提供 Windows Chrome Cookie 读取、Chrome 调试端口同步和保守合并逻辑。它的文档明确写出：滑块验证、`x5sec`、登录过期和风控校验属于平台侧状态，代码不能保证自动解决。

这条路线比服务器端重新创建浏览器会话更接近实际登录设备：登录、人工验证和后续 Cookie 采集在同一台机器、同一浏览器环境中完成。

### 2. Cookie 只在确认可用后替换

上述项目会校验关键 Cookie（例如 `unb`、`_m_h5_tk`），只有候选 Cookie 完整且可用时才替换当前值。失败时保留旧 Cookie，避免一次失败把仍可能可用的会话清掉。

### 3. 风控停止重试

`zhinianboke/xianyu-auto-reply` 和相关项目都有登录日志、冷却或重试上限等机制。公开 Issue 仍记录了滑块视觉成功但没有新 `x5sec`、手动更新 Cookie 后再次重试失败等情况，说明“继续重试”不是解决方案。

### 4. 账号级隔离

成熟项目将账号、Cookie、登录日志和连接状态按账号分开保存。实际迁移时应让每个账号拥有独立浏览器 profile、Cookie、设备信息、速率限制和风控暂停状态，不要让多个账号共享一个远程浏览器上下文。

## 不建议照搬

- 远程滑块 Solver、未知镜像或公共 Cookie 同步服务。
- 只根据页面动画或截图判断验证成功。
- 验证失败后每几分钟持续刷新 Token。
- 在日志、告警或仓库里输出完整 Cookie、Token、验证 URL。
- 把“被挤爆啦”等临时繁忙响应当成 Cookie 失效。
- 以“70% 成功率”“商业级求解”等 README 宣传语替代真实的服务端放行验证。

## 与当前项目的差距

当前项目已经有账号级风控状态、人工验证入口、连接退避和 Token 保护，但仍有架构差距：

1. 登录入口仍以服务器端 Playwright/协议 Cookie 接管为主，无法保证与用户完成验证的真实浏览器环境一致。
2. 账号没有完整的“本机浏览器 profile -> 会话凭据 -> 后台接管”生命周期。
3. 登录失败、手机号验证、滑块验证、Cookie 过期和服务器拒绝需要在 UI 中分成不同状态，不能都显示为“登录失败”。
4. 需要把“验证完成”定义为后续真实 Token/连接成功，而不是滑块页面关闭或截图变化。
5. 生产环境应在风控后暂停该账号的所有自动任务，避免自动回复、发货、商品同步继续撞接口。

## 建议的迁移路线

### 阶段 A：停止扩大损失

- 暂停当前两个账号的自动 Token 刷新、自动重连和后台任务。
- 不再尝试远程滑块破解、未知 Solver 或批量重试。
- 保留现有 Cookie 和日志，但不要在工单或聊天中发送明文凭据。

### 阶段 B：本机登录接管

- 每个账号在本机 Chrome/Chromium 使用独立 profile 登录。
- 用户在同一 profile 中完成扫码、手机号验证或滑块验证。
- 只有登录页和消息页确认可访问、关键 Cookie 完整、一次低频 Token 探测成功后，才把会话交给后台。
- 后台只保存加密后的必要凭据，不把验证码过程搬到服务器。

### 阶段 C：低频后台运行

- 连接健康时不主动重启 Token。
- 临近真实过期时间再刷新；收到风控后按 30 分钟、1 小时、2 小时、4 小时、6 小时退避探测。
- 任一账号触发风控时，暂停该账号任务并要求人工恢复；不影响其他账号。

### 阶段 D：可验证恢复

- UI 显示“需要手机号验证”“需要滑块验证”“Cookie 过期”“服务器拒绝”“暂时繁忙”五种不同状态。
- 恢复按钮只做一次探测；只有后续 Token 和 WebSocket ACK 都成功才显示在线。
- 增加登录尝试、风控事件、最后成功时间和暂停原因的历史记录。

## 当前决策

本轮不发布“自动绕过风控”的新版本。下一步应在确认用户愿意采用“本机浏览器登录 + 后台连接”后，再单独设计迁移分支和回滚方案。这个方案不能承诺第三方平台 100% 放行，但能避免当前服务器会话与人工验证会话不一致的问题。
