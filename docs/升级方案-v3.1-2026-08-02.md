### 1.3 现状问题

1. **版本号不统一**：`pom.xml` = 2.2.0，`README.md` 仍写 v2.1.11，前端 `package.json` = 2.2.0 → 无单一版本源。
2. **无模块级版本**：数据库表结构、前端模块均无独立版本号，回退只能靠整体备份。
3. **缺少卖家核心闭环**：能同步商品、能发货，但**不能发布/上架商品**、不能下架、不能批量改价。
4. **限流依赖单一**：仅有 `XianyuAuthFailureGuard` 认证失败保护，缺写操作限流（令牌桶）与风控熔断分级。
5. **通知渠道不完整**：缺 Bark / Telegram / ntfy 等海外与苹果生态渠道。

## 四、版本号管理策略（核心诉求：方便回退）

### 4.1 三层版本体系

```
版本 = 应用版本(Major.Minor.Patch) + 数据库版本(Schema) + 功能版本(Feature)
```

| 层 | 标识 | 载体 | 说明 |
| --- | --- | --- | --- |
| 应用版本 | `2.2.0` → `3.0.0` | pom.xml（单一来源） | README/前端 package.json 由构建生成或人工同步，发布时 git tag `v3.0.0` |
| 数据库版本 | `schema_version` 表 + `migrations/` 目录 | SQLite 内表 | 每个迁移一个编号（如 `V3_1__add_publish.sql`），启动时按序应用并记录，**回退 = 恢复到上一个版本号 + 备份还原** |
| 功能版本 | `F1.1 商品发布` | CHANGELOG + 模块目录 | 每个功能合入时记录功能版本号，便于精确知道"哪个功能从哪个版本开始存在" |

### 4.2 回退流程（三步）

1. **发布前**：自动备份 `dbdata` + 导出全量数据（已有 DataBackupService，每 12 小时自动备份 + 手动导出）。
2. **标记**：git tag `v3.1.0`（可回退点），CHANGELOG 记录该版本 schema 版本号。
3. **回退**：`git checkout v3.0.0 && mvnw clean package` → 还原备份的 `dbdata` → 启动（迁移器检测到 schema 版本低于当前，自动跳过已应用迁移）。生产部署已有健康检查与失败回滚（deploy-production.yml）。

### 4.3 版本规划表

| 版本 | 主题 | 核心内容 | schema 版本 |
| --- | --- | --- | --- |
| **v3.0.0** | 卖家运营闭环 | F1 商品发布/下架、F2 限流护栏、A2 schema 版本化、A1 统一版本源 | V3_1 |

## 六、风险与注意事项

1. **发布接口稳定性**：闲鱼 mtop 发布链路复杂（类目/图片/风控），先灰度真实账号，失败不落库订单。
2. **限流误伤**：令牌桶参数需按账号调整，避免限制正常发货流程（发货走独立额度）。
3. **代理可用性**：代理池质量决定成功率，默认关闭，配置开启。
4. **Schema 迁移**：所有表结构变更必须走迁移器，禁止直接改 DDL 脚本。
5. **合规**：仅用于自有账号自动化运营，遵循闲鱼用户协议（同 goofish-cli 合规声明）。
